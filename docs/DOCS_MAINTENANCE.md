# Keeping the documentation in step with the code

This is the procedure for the user documentation of SoundCraft / SML Studio: the manual
([USER_GUIDE.md](USER_GUIDE.md)), the generated references, the external-operator (Grok) guide and
the documentation manifest. It is part of development: a change is not finished until its
documentation is. Nothing here runs by itself in the background. Each step is either run by a
command (generated material), or done and reviewed by whoever changes the behaviour.

## What is generated and what is reviewed

| Material | How it is produced | Who keeps it true |
|---|---|---|
| [COMMAND_REFERENCE.md](COMMAND_REFERENCE.md), [reference/commands.json](reference/commands.json), [reference/SHORTCUTS.md](reference/SHORTCUTS.md), [reference/CAPABILITIES.md](reference/CAPABILITIES.md) | **Generated** by `cargo xtask docs` from the command registry (ids, labels, menus, parameter docs, undo, risk, status), the stated limits (`help.limits`), both shortcut tables, the UI-layer commands, the control-channel methods (`crates/ui-egui/src/control.rs`) and the MCP tools (`crates/automation/src/mcp.rs`) | The generator. Never edit by hand. `cargo xtask docs-check` (part of `cargo xtask ci`) fails when these files differ from what the current source would produce. |
| [USER_GUIDE.md](USER_GUIDE.md) (the manual) | Written by people (or agents) from the implementation, tests and observation | **Implementation review.** The author of a behaviour change updates the affected chapters in the same change. |
| [grok/GROK_OPERATOR_GUIDE.md](grok/GROK_OPERATOR_GUIDE.md), [grok/GROK_BOT_INSTRUCTIONS.md](grok/GROK_BOT_INSTRUCTIONS.md) | Written | Implementation review, whenever a control path, a command an operator relies on, a capability or a safety rule changes. |
| [DOCS_MANIFEST.json](DOCS_MANIFEST.json) | Written; checked by `docs-check` | The person who verifies. Its `verification` block is advanced **only** after the verification it describes was done (below). |
| [DOCS_CHANGELOG.md](DOCS_CHANGELOG.md) | Written | One entry per documentation change. |
| HTML/PDF companions and the Grok ZIP | Generated by `python3 packaging/docs/build_docs.py --html --pdf --zip OUT.zip` (pandoc; Chromium/Chrome for PDF) | Rebuilt from the Markdown, never edited; the script checks every link inside the bundle and the rendered HTML/PDF. |

`USER_GUIDE.md` is also compiled into the application: the internal assistant (Help ›
Assistant) cites its `## N. Title` headings as "guide §N". Keep that heading form, keep titles
descriptive, and remember that renumbering changes what the assistant of later builds cites.
Older builds keep citing the guide they were built with; that copy is archived in
[manual_archive/](manual_archive/) whenever a numbering change is made.

## When documentation must change

Update the documentation in the same commit (or the same pull request) whenever a change
alters any of: what a command does, its parameters, label, menu path or default chord; a UI
label, window or control; a shortcut profile; an error or refusal message a user sees; a stated
limit; plugin, platform, device or format compatibility; the signal order; export, recovery or
safety behaviour; the control channel, MCP or CLI; or what an external operator may rely on.

## Procedure for a behaviour change

1. **Find the chapters.** [DOCS_MANIFEST.json](DOCS_MANIFEST.json) `chapters` maps each manual
   chapter to the commands and source files it describes. `cargo xtask docs-check` prints
   `REVIEW chapter …` for every chapter whose source files changed since the commit the
   documentation was last verified against. Treat that list as the minimum.
2. **Regenerate.** `cargo xtask docs`, then read the diff of the generated files: it shows
   every new, removed or changed command, chord and limit.
3. **Edit the chapters** to describe the new behaviour exactly as implemented: control names as
   they appear on screen, command ids, ordered steps, expected result, undo and recovery,
   limitations. Do not describe planned work as available. If a feature exists in code but has not
   been observed working on the target platform, say so with the evidence label (manual §1).
4. **Update the operator guide** if operators are affected (new command they should use, a
   changed refusal, a changed safety rule, a new or removed control method).
5. **Capability status.** Update the table in manual §2 when a capability changes state.
6. **Changelog.** Add an entry to [DOCS_CHANGELOG.md](DOCS_CHANGELOG.md): date, source commit,
   chapters changed, why.
7. **Check.** `cargo xtask docs-check` must pass (links, anchors, every command named in
   backticks exists, generated files current, version matches). It runs inside `cargo xtask ci`.

## Advancing the "verified" state

`DOCS_MANIFEST.json` → `verification` records the source commit the documentation was checked
against, the date, what kind of verification was done and what remains pending. Change it only
after doing that verification:

- **Source review** — every chapter flagged by `docs-check` was read against the code and tests at
  that commit. Set `source_sha` to that commit, `date`, `method: "source review + portable tests"`.
- **Observed** — a procedure was carried out on a named machine with a named build. Record it in
  `observed` (build hash, machine, procedure, result). Never record an observation that did not
  happen; never copy one forward to a new build without repeating it.

Do not advance `source_sha` to make the drift report quiet. If you have not reviewed a flagged
chapter, leave `source_sha` where it is; the next person sees the same list.

## Versions

- `product_version` in the manifest and the "version X.Y.Z" line in the manual header must match
  the workspace version; `docs-check` fails otherwise. Bump them together with
  `cargo xtask version set X.Y.Z` only after the manual has been reviewed for that release.
- The manual is compiled into the application, so any change to `USER_GUIDE.md` produces new
  executables with new hashes even when no program code changed. Record each published build in
  `known_builds` with its own hashes.
- The application reports only its version number (`--version`, Help › About); it does not embed
  a commit hash. Packages carry a `MANIFEST.json` with the commit and per-file SHA-256 hashes
  (`packaging/windows/cross-build.sh`, `docs/remote_continuation/tools/linux_manifest.py`). The
  manifest's `known_builds` lists builds with their executable hashes so an installed copy can be
  identified (manual §3.4, Grok guide "Identify the build").

## Packaging

Every package built by the repository scripts includes the documentation snapshot of its
source: `packaging/docs/build_docs.py --bundle-dir DIR` copies the bundle file set into the
package (Windows cross-build zip from `cross-build.sh`: `docs\`, recorded in its `MANIFEST.json`;
Linux packages from `package.sh`: `share/doc/soundcraft/manual/`; Windows portable zip from
`package.ps1`: `docs\`). The MSI does not include it yet (needs WiX component entries). The bundle carries `DOCS_MANIFEST.json`, so whoever opens it
can see which source and which verification it describes.

## Grok / external operators

The Grok guide tells the operator to compare the installed build with
`DOCS_MANIFEST.json` → `known_builds` at the start of every task and to reload the matching
documentation when the build changes. When you publish a new build, add it to `known_builds`
(version, commit, executable SHA-256 hashes) and rebuild the Grok ZIP
(`packaging/docs/build_docs.py --zip OUT.zip`).
