# Clock and low-latency engine contract — revision 1.7
Status: PLANNED / target hardware access unknown. This is a foundation requirement, ahead of new mixer UI. Exactly four sprints and six-hour cap remain. Native summing/tape sound models stay deferred by owner.

## CL01 — audio-owned timebase
Use one monotonic integer frame counter for each running device stream, separate from signed session sample position, which can seek/loop. Carry a stream-generation ID across stop/restart/device changes so stale timestamps cannot be reused. One logical transport owner maps device frames to session frames and tempo. Do not advance musical time from GUI repaint, wall-clock time, sleep intervals or disk-writer completion. Render cursor, hardware presentation cursor and capture cursor are distinct and labeled in diagnostics. Playhead follows estimated audible presentation, not simply the end of a prefetched render buffer.

Backend returns actual sample rate, callback frame count, device position/timestamp when available, reported input/output latency and provenance/uncertainty. Never treat an unavailable measurement as zero. Use checked unit conversions and rational/remainder-preserving tempo mapping; no accumulated rounding drift. Automation, click/count-in, punch, loops and nudge operate at explicit sample offsets within a block; split processing or use host sample-offset events as appropriate. UI extrapolation may animate between snapshots but never controls the audio clock.

Single interface for input/output is the supported low-latency baseline. Nominally equal sample rates on independent devices do not establish clock lock. Reject unsupported aggregate devices rather than silently dropping/repeating samples. Drift-correcting aggregate-device resampling and external word-clock/MTC sync are outside this pass. Surface device clock lock only if the backend reports it; otherwise show Unknown. Offline rendering uses deterministic sample progression without waiting for real time. Silent-device fallback is labeled Offline/No Audio Device and cannot report successful physical capture.

## CL02 — actual device/buffer negotiation
Expose backend/device, sample rate, requested buffer and actual effective callback size/range and reported hardware buffer, separately when these differ. Windows target: implement/verify the interface vendor's ASIO path if the framework/build dependencies support it; do not assume CPAL default host implies ASIO. Audit pinned CPAL/workspace features, required SDK/build setup and existing backend before implementation. Preserve WASAPI fallback and label its actual mode; do not imply exclusive mode if unsupported. No silent backend switch during a take. No new hardware purchase or owner-system driver install is authorized by this prompt.

Try 64/128 frames at 48 kHz when the driver offers them; 32 is optional. Also validate 256/512/1024 where supported. 44.1 kHz remains supported; 96 kHz is optional, not a mandatory shortcut to lower latency. Change device/rate/buffer only stopped, prepare off callback, invalidate relevant calibration, then reopen and display negotiated values. On failure restore known configuration or enter explicit stopped/error state. Never alter sample rate or buffer silently to hide xruns.

Remove unconditional 512-frame batching from the live path if the callsite audit confirms it causes avoidable queued audio or delayed commands. Support variable callback sizes and bounded preallocated max blocks. Process only required frames or justified subblocks; clear stale pending audio on seek/stop safely. Preserve plugin declared block constraints; any adapter FIFO latency is explicit and compensated. Do not merely rename BLOCK or expose a buffer UI without changing actual processing.

## CL03 — Tracking / Mixing / Hardware Monitor
Tracking: use a supported small device buffer, identify all live-input downstream paths including sends, buses, summing/tape slots and Main. Display latency contributions and high-latency processors. Provide explicit user-selected bypass/disable choices for lookahead/oversampling-heavy processors. Bypassing a plugin often retains its latency, so a stopped graph rebuild/deactivation is required when removing latency. Show changes; preserve normal states for restoration. Do not silently change sound to meet a number.

Mixing: full processing and delay compensation; larger user-selected buffer permitted. Both modes use the same processing algorithms and session parameter IDs. SL05 owns the export policy for temporary tracking/audition overrides: normal saved graph for both real-time and offline export, with explicit difference notice. Mode switching that changes device/graph latency occurs stopped. A future dual-buffer/anticipative engine may be useful, but is deferred until the single-buffer graph meets its gates. No HDX-style DSP mode claim.

Hardware Monitor: software dry monitoring off for the armed channel, playback still on; user controls interface direct monitoring. Explain that plugin processing is not on the direct hardware path. Do not claim the app can switch the hardware mixer without an actual supported API. Avoid simultaneous dry hardware plus dry software monitoring. Recording stays dry in every mode; wet printing is a separately explicit existing export/print action, not an automatic mode effect.

## CL04 — compensation and recording placement
Maintain per-node latency and longest-path compensation for outputs, sends, parallel chains and supported sidechains. Include every hosted insert, slot, adapter FIFO and source hook. A plugin latency change during recording is a capture-integrity event: finalize committed capture safely, stop transport with a named latency-change error, rebuild off callback and require explicit resume. Do not silently continue with known-wrong alignment. During playback only, stop/rebuild or validated equivalent transition before further aligned playback; report the interruption. Preserve existing per-slot bypass compensation behavior from SL03/05. Tracking graph changes may remove latency only through an explicit stopped transition; compensation elsewhere still aligns paths.

Capture file frames retain their order and count. Place takes using backend timestamps plus a documented latency ledger, not GUI cursor at callback arrival. Separate driver-provided compensation, additional measured residual offset and manual offset. Record sign and units; subtract each contribution exactly once. Calibration keyed by backend/device/driver/rate/buffer/channel route/monitor topology; invalidate on relevant changes. Ordinary loopback measures combined output/input delay and cannot independently identify converter input delay. Apply only the residual needed by the defined overdub path, not the full measured total on top of already applied compensation.

Native calibration uses a safe line-output-to-line-input loopback with monitoring/feedback disabled, no mic phantom power, at least 100 spaced known impulses or correlation bursts over 60 seconds, repeated after reopen. Log raw offsets, median, spread, outliers and uncertainty; no fake sample-exact claim on unstable hardware. Headless clocks have exact fixtures. Hardware residual goal <=1 sample when a stable same-clock path actually supports that confidence; otherwise report measured error and block the precision claim. User monitoring delay remains a separate measurement.

## CL05 — bounded real-time work and UI response
Audit callback allocations/deallocations, locking, plugin state capture, channels, graph swaps and worker scheduling. No file/UI work, unbounded queue draining, heap growth, blocking lock or final Arc/plugin destruction on audio threads. Bounded preallocated queues/coalesced continuous changes; discrete transport commands and final gesture values cannot be silently lost. Serialize plugin state only under a host-supported safe strategy, using stopped quiescence if necessary; do not assume running-state capture is real-time-safe.

Reuse fixed worker pools where present. Schedule only independent ready graph nodes; serial plugin chains cannot become parallel by adding threads. Benchmark single worker against additional workers and record critical-path time. No thread creation per callback, unbounded spin or cross-core barrier on an unrelated slow task. Use OS audio scheduling support where available without changing global system priorities. Disk writer, waveform generation, scan and editor creation stay off audio threads. A slow UI/plugin editor cannot block capture; actual plugin DSP overruns are reported as xruns, not concealed.

Record UI event -> model acknowledgment -> other-view render separately from event -> audible gain/transport change. Gain smoothing is accounted for, not disguised as queue delay. Transport click/keyboard events are accepted by the next processing boundary after dequeue; requested future punch/click events execute at exact sample offsets. Publish start/stop/seek acknowledgment and audible onset distributions separately. No “instant” promise based only on FPS.

## CL06 — performance panel and proposed targets
Show sample rate, requested/effective buffer, estimated input/output/monitor latency with provenance, measured calibration status, worst live path/plugin contributors, callback load and xrun count. Keep advanced diagnostics collapsible.

At 48 kHz, 64 frames lasts 1.333 ms and 128 lasts 2.667 ms. Two such buffers total 2.667/5.333 ms respectively; these are arithmetic components ONLY and exclude converters, driver safety queues, adapters and plugin delay.

| Measure | Current proposed acceptance | Stretch / comparison |
|---|---|---|
| Physical software-monitor input-to-output | <=10 ms at a stable supported 64/128 setting, clean live path | <=5 ms when hardware permits |
| Native Pro Tools/Reason comparison | Required only for equivalence claim; same machine/device/driver/rate/buffer/path | Target no more than 1 ms additional measured delay, with uncertainty reported |
| Shared mixer visual response | p95 <=50 ms, prior frame/stall gates retained | Characterize p99/max, not only average |
| Callback work | p99 <80% of frames actually serviced / sample rate, zero missed deadlines/xruns in target run | Record max and device errors; average CPU cannot pass |
| Recording placement | exact headless offsets; hardware goal <=1 sample after valid residual calibration | Declare uncertainty and stability before claiming precision |
| Capture stability | zero lost/duplicated frames in 30-minute same-interface test | No app-induced frame-count drift; report physical clock/timestamp uncertainty separately |

<=10 ms supersedes the previous <=20 ms aspirational monitoring gate. Missing target hardware means BLOCKED FOR TARGET VALIDATION, not a software pass or automatic failure. If even the matched native reference cannot reach 10 ms on the chosen hardware, report limitation and best stable result; do not silently relax the target or claim parity. These are goals, not observed achievements.

## Audit measurement clarifications
Clock domains: same physical interface is a baseline, not proof of identical callback phase. Align input/output timestamp epochs and report their reliability. Reject unsupported rate/device combinations; support mismatched playback-file rates via named existing resampling boundaries, not hidden live capture resampling. Sample-rate changes are stopped and reset generation/calibration as described.

Realtime load denominator is N/Fs for frames serviced, not the wall gap since the previous callback: using a delayed callback's enlarged wall gap can falsely improve the load percentage. Log compute duration, interval jitter, deadline misses and queue depth separately. Zero xruns and the p99 headroom requirement both apply; a favorable percentile cannot excuse a missed deadline. Empty/identity graph command dispatch is bounded to one device block after accepted timestamp under idle queue plus reported pending output. Measure event-to-audible response including pending output; “after dequeue” alone cannot hide a long queue.

Physical monitoring probe: use the same test signal split to the DAW input and an independent reference capture channel; record monitored DAW output alongside that reference, with recorder-channel skew measured/removed. An equivalent same-interface two-input arrangement is allowed only when routing isolates reference/capture from feedback and its timing cancellation is demonstrated. Name the topology and uncertainty. Output-to-input DAW loopback remains valid for the declared overdub offset test, but is not automatically a measurement of input-to-output monitoring. A known delay fixture should increase measured monitoring delay by its declared samples within uncertainty, testing the measurement itself.

Calibration must use the exact replay timestamp/driver-ledger definition. Offset sign test: known late placement (+D) requires -D residual correction; driver-covered terms must not be counted twice. Retain raw file samples and change placement metadata only. A residual >1 sample or unstable estimates blocks a sample-precision claim; physical target readiness remains governed by the actual measured/declared uncertainty, not invented precision.
