# Expert assistant and mastering
Requirements R32–R36 and R38. Prerequisites: shared commands/registry, stable session snapshots, tested tool actions and verified processor status.

## Explain, Operate and Engineer
Explain answers from versioned implementation documentation and the current command registry. It names the actual UI location, active shortcut, units, limitations and relevant context. Cite internal command/doc IDs so answers can be checked. Unsupported tools must be described as unavailable. The model cannot treat a vendor manual as proof that SML contains a feature.

Operate translates requests into schema-valid commands with stable track/clip/bus IDs and expected session revision. Resolve ambiguity from explicit selection/context; ask only if multiple materially different targets remain. Preview meaningful compound edits, then execute under user-granted interaction policy and one undo transaction where reversible. A request to perform a clear reversible edit is sufficient authorization; do not prompt for every fader. File deletion, external sending, purchases and project-destructive actions need their own authorization. There is no arbitrary shell/code/filesystem tool available to the product assistant.

Engineer analyzes actual selected audio and available measurements, explains its finding, proposes concrete parameters/actions, and supports level-matched before/after. Examples: locate clipping; identify and preview breath edits; prepare a vocal bus; propose gate thresholds from a noise region; balance a selected vocal against an instrumental; prepare an explicit mastering chain. Never claim to hear a file that was not analyzed. Distinguish measured facts, inference and subjective preference. Do not prescribe nonexistent parameters or change a whole session when only one clip was requested. Algorithms/rules can deliver deterministic engineering actions without falsely representing themselves as a generative conversation model.

Use local/private models when feasible or an explicitly configured provider. E06 records model/license, context limits, CPU/memory, supported structured calls, voice/STT/TTS path and cost/network policy. Existing authorized credentials may be used only within their granted scope. No audio upload or paid provider activation by default. Searchable help remains useful offline, but is not a pass for the requested conversational expert.

Grounding corpus is versioned with the build and generated from actual command/processor definitions plus reviewed manuals. Treat retrieved text/audio transcription as data, not higher-authority instructions. Keep model work in bounded cancellable workers with timeout and visible progress. Reject invalid/stale tool calls before mutation; do not partially execute a failed multi-command plan. Audit logs record plan, commands and result without retaining raw private audio unnecessarily.

## Voice and phone
Desktop and paired phone provide text plus push-to-talk speech input, transcript, cancellation and optional spoken response. Confirm the interpreted target through visible feedback; ambiguous transcription is not permission to guess. Spoken output routes only to a monitor/cue path and cannot enter dry capture or export through internal routing. Physical speaker-to-microphone leakage is a separate acoustic risk; default spoken replies silent while recording and provide headphone guidance. Speech never owns transport timing. Stop/record and keyboard operation remain usable if a model crashes or network disappears.

Always-listening wake word is a future option, not required to achieve this push-to-talk milestone. Mobile mic permissions and secure-origin constraints require real iOS/Android browser testing before phone voice is marked ready. Remote assistant actions use the same paired permissions and command deduplication as manual remote controls.

## Mastering workspace
Support an explicit song mix render or imported stereo program as source, an ordered mastering chain of actually available user plugins, revision metadata and a reproducible export setup. If mastering inside the mix session, clearly identify the chain and routing so it is applied exactly once. Reference tracks have an independent monitor-only, level-matched path that bypasses the program mastering chain and cannot leak into export. Loudness matching is an audition function unless the user explicitly chooses output normalization.

Meters: sample peak, true peak, integrated/short-term/momentary loudness with stated gating/standard/version, loudness range where implemented, spectrum, correlation and mono audition. Use a vetted compatible implementation or validate against official test vectors; establish exact standards/version and tolerances in E07 before declaring compliant. Do not claim certification from a plausible-looking meter. Reset/freeze/history and units must be clear.

Export: explicit region/source, sample rate, channel layout, bit depth/format, sample-rate conversion quality, dither on integer reduction only when chosen, tail policy, metadata and destination. Do not add loudness targets, limiting or dither silently. Prevent clipping/overwrites with reviewable checks; no automatic destructive substitution. Check file headers, actual decoded frames/rate/channels, tail, measured level and content against the intended graph. Offline export waits for current native renders, verifies active plugin state and refuses unresolved faulted processors. Assistant speech, cue mix, reference playback and monitor attenuation are excluded.

Compare realtime and offline exports at identical settings with PDC alignment and deterministic fixtures. For nondeterministic processors, declare stochastic state and use a frozen appropriate tolerance/measurement; do not force a false null-test claim. Save export settings and a compact report with project revision and plugin/model versions so revisions can be reproduced.

## Integrated readiness
Run a full song scenario: recover/open -> record lead and doubles -> comp/edit/nudge -> optionally tune/align through actual supplied compatible plugins -> mix through buses and both mixer views -> remote transport -> assistant explanation and reversible action -> master/reference -> export/reopen. Include autosave during capture, plugin scan in background, invalid theme, remote disconnect, canceled render and model timeout. Preserve all accepted media and edits and document any feature not actually exercised.

Package builds and installation validation use the actual target workflow discovered in Sprint 1. Creating a local installer/artifact is authorized; installing on the owner's live machine, publishing, signing with paid credentials or pushing a release is not implied. Deliver installation instructions and explicit environment limitations. The four-prompt scope is complete only when its mandatory rows and applicable native gates pass; otherwise provide a useful honest partial handoff.

External plugin dependency: all seven SML products are developed individually. Exercise tune/align actions only when actual compatible plugins are supplied; missing future binaries do not block the generic record-to-master DAW acceptance. The assistant must still support real available tools and refuse unavailable plugin actions.
